# 報表時間區間 — 方案比較分析

## 背景

- **產品階段**：新產品 MVP，正在驗證市場是否買單
- **主要使用者**：集團大老闆（高階主管）
- **使用情境**：月會、季會、年度檢討等高層決策場景
- **訪談已知需求**：
  - 想要能調整時間區間
  - 有看季度數據的需求

---

## 評估維度

針對「大老闆 + MVP」這個組合，方案評估著重於以下五點：

| 維度 | 說明 |
|---|---|
| **滿足訪談需求** | 是否覆蓋「時間調整 + 季度」兩個明確訊號 |
| **使用情境匹配度** | 是否符合高階主管「看完整期間、看趨勢、看對比」的習慣 |
| **MVP 實作成本** | 工時、複雜度、後端配合度 |
| **資料語意清晰度** | 數字不會誤導使用者（例如 KPI 該是總和還平均） |
| **未來延展性** | 若市場買單，後續擴充的成本 |

---

## 三個方案

### A 方案 — 僅 By 月

**樣貌**
- 切換器：只有「月份」選擇器
- KPI 小卡：當月數值
- 趨勢圖：所選月份往前推 12 個月（by 月）

**優點**
- 實作最簡單，前後端負擔小
- 時間粒度單一，沒有任何語意混淆

**缺點**
- **直接違背訪談需求**：無法看季度、無法看年度
- 大老闆若想知道「Q1 表現如何」只能自己心算 1–3 月加總，體驗差
- 無法支援月會以外的會議場景

---

### A+ 方案 — 月 / 季 / 年 Tab

**樣貌**
- 切換器：三個 Tab（月 / 季 / 年），每個 Tab 各自選擇期間
- KPI 小卡：所選期間的數值（單月 / 單季 / 單年）
- 趨勢圖：與 KPI 同粒度往回看
  - 月 Tab → 近 12 個月 by 月
  - 季 Tab → 近 8 季 by 季
  - 年 Tab → 近 3～5 年 by 年
- 預設顯示「上一個完整期間」（例如本季尚未結束，預設秀上一季）

**優點**
- **完全對應大老闆的工作節奏**：月會看月、季會看季、年度看年
- **滿足訪談需求**：時間可調 ✓、可看季度 ✓
- KPI 與趨勢圖**粒度一致**，沒有「平均 vs 總和」的語意問題
- 實作成本中等，後端只需提供 月 / 季 / 年 三種聚合 API
- UI 邏輯清晰，使用者學習成本低（三個 Tab 而已）

**缺點**
- 無法看「自訂區間」（例如「3 月到 5 月」這種跨季組合）
- 年 Tab 在資料累積不足時意義有限（需要 3 年以上才看得出趨勢）
- 「進行中期間」需特別處理（預設顯示上一完整期間，避免誤導）

---

### B 方案 — 彈性區間（年 / 月 / 自訂）

**樣貌**
- 切換器：快速 Chip（本月 / 近 3 個月 / 近 6 個月 / 近 1 年）+ 自訂日期區間
- KPI 小卡：所選區間的**平均值或總和**（依指標類型）
- 趨勢圖：依區間長度動態切換粒度（日 / 月）

**優點**
- 彈性最高，理論上滿足所有時間查詢需求
- 自訂區間可支援特殊分析（例如某活動期間的成效）

**缺點**
- **KPI 語意風險高**：不同指標需要不同聚合方式
  - 入住率、滿床率：應顯示**區間平均**（不可加總）
  - 入住人次、營收：應顯示**區間總和**
  - 在住人數、員工數：應顯示**區間末值（snapshot）**
  - 若未明確標註，大老闆容易誤讀（例如把「年區間入住率」誤判為破千百分比）
- 趨勢圖粒度動態切換邏輯複雜，且部分指標沒有日資料時要 fallback
- 「自訂日期區間」對大老闆是相對低頻的功能，但實作成本佔比高
- UI 比 A+ 複雜，需 chip + date picker，學習成本較高

---

## 方案比較總表

| 維度 | A 方案 | A+ 方案 | B 方案 |
|---|---|---|---|
| 滿足「時間可調」訪談需求 | ❌ | ✅ | ✅ |
| 滿足「看季度」訪談需求 | ❌ | ✅ | ✅（需手動選 3 個月） |
| 大老闆使用情境匹配度 | 低 | **高** | 中 |
| KPI 語意清晰度 | 高 | **高** | 低（需逐一標註） |
| 趨勢圖實作複雜度 | 低 | 低 | 高（動態粒度） |
| MVP 實作工時 | S | **M** | L |
| 未來延展性 | 低（要打掉重練） | 中（可疊加自訂區間） | 高 |
| UI 學習成本 | 低 | 低 | 中 |

---

## 適用情境分析

### 大老闆的觀看習慣

| 場景 | 想看的數據 | 適合的方案 |
|---|---|---|
| 月會匯報 | 上個月完整數據 vs 前月 / 去年同月 | A、A+、B 皆可 |
| 季會匯報 | 上一季完整數據 vs 上季 / 去年同季 | A+、B |
| 年度檢討 | 去年完整數據 vs 前幾年 | A+、B |
| 隨手查特定區間 | 例如「過年期間入住變化」 | 只有 B 完整支援 |

大老闆**最常的三種場景**（月會 / 季會 / 年度）剛好就是 A+ 的三個 Tab，匹配度最高。

「隨手查自訂區間」是相對低頻的需求，MVP 階段不一定要先做。

---

### MVP 階段的取捨

| 考量 | 偏好方向 |
|---|---|
| 市場還沒驗證，避免過度設計 | 偏 A+（中等複雜度），不偏 B（高複雜度） |
| 訪談已有明確訊號，必須回應 | 排除 A（不滿足季度需求） |
| 後續若市場買單，希望好延展 | A+ 可疊加「自訂區間」演化成 B；不需要重構 |
| 大老闆使用，數字不能誤導 | 偏 A+（語意單純），B 需要更多保護機制 |

---

## 風險與待釐清事項

無論選哪個方案，以下幾點需要先確認：

1. **資料粒度**：後端目前提供的資料是否已有月 / 季 / 年聚合？還是只有日資料？
2. **資料累積年限**：年 Tab 若只有 1～2 年資料，趨勢圖意義有限，要不要先隱藏年 Tab？
3. **進行中期間處理**：當期數據要不要顯示？預設秀上一完整期間還是當期？
4. **指標清單盤點**：每個 KPI 屬於 sum / avg / snapshot 哪一類？（B 方案需要、A+ 也建議做以利未來擴充）
5. **對照基準**：是否要在 KPI 卡片上同時顯示「vs 上期」「vs 去年同期」的變化？

---

## 建議方向

**MVP 推薦走 A+ 方案**，理由：

1. ✅ 完整回應訪談中「時間可調」「看季度」兩個訊號
2. ✅ 三個 Tab 對應大老闆三種主要會議節奏（月會 / 季會 / 年會）
3. ✅ KPI 與趨勢圖粒度一致，數字不會誤導
4. ✅ 實作成本適中，適合 MVP 階段
5. ✅ 若市場買單，未來可在 A+ 上**疊加**自訂區間，演化成 B，不需打掉重練

**A+ 的最小可行配置（MVP 建議起點）**：
- 三個 Tab：月、季、年（若年資料不足可先只做月 + 季）
- 每個 Tab 預設顯示「上一個完整期間」
- KPI 卡片附上「vs 上期 / vs 去年同期」對照
- 不做自訂區間（等使用者明確要求再加）

**驗證指標（觀察是否需升級到 B）**：
- 使用者是否常切換到非預設期間？→ 顯示「自訂區間」需求強度
- 是否有人反映想看跨季 / 月底跨月區間？→ B 方案的觸發點
